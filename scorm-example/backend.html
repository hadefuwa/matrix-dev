Authoring goal

Write the Word source so each learner-facing item can become a clean, packageable asset.

The best SCORM-ready source is not just tagged. It separates learner pages cleanly, uses predictable filenames, keeps each assessment in its own HTML block, and records the five SCORM decisions explicitly instead of leaving them to be inferred later.

Use one tagged block per deliverable file.

Authoring rules for the best SCORM-compliant resource pack

These rules tell the course author how to prepare the Word document before the pipeline runs, so the generated browser files and later SCORM package are both easier to validate.

Structure

Keep one real output per tagged block

  • Start every publishable item with a recognised opening tag and end it with the exact matching closing tag.
  • Put only one learner resource inside each block. Do not combine two assignments, two worksheets, or mixed output types in one tag pair.
  • Keep planning notes, teacher-only comments, and draft instructions outside publishable blocks unless they are meant to appear to learners.
Naming

Give every block a unique, correctly typed filename

  • Add a <filename> line inside every block and wrap the filename in double quotes.
  • Make the filename unique across the whole document so the pipeline never has to guess which file wins.
  • Match the extension to the block type: .html for <HTML>, .docx for worksheets, and the intended document type for references.
SCORM fit

Author trackable learner pages as HTML-first content

  • Use <HTML> for pages the LMS may launch or track, especially homework, assignments, quizzes, and assessments.
  • Keep a clear title at the top of the block so the built page and manifest labels are human-readable.
  • Make each assessable item self-contained so it can become its own SCO entry if required.
Clean content

Write source content that can publish without manual cleanup

  • Keep learner instructions, questions, tables, and reference text inside the block, but remove author reminders that should not appear in the final output.
  • Use stable wording for headings and task labels so generated navigation stays consistent across outputs.
  • Do not rely on formatting alone to signal meaning. Put key structure into the text itself so extraction does not lose it.
Boundaries

Separate trackable content from supporting files

  • Use <worksheet> for printable or downloadable activity sheets that are not expected to be LMS-tracked.
  • Use <document> for certificates, reference PDFs, or supporting resources that sit alongside the course.
  • Do not expect worksheet or document blocks to become trackable SCOs unless they are rebuilt as HTML launchable pages.
Definitions

Record the SCORM decisions explicitly

  • State the SCORM version, launch file, tracking model, completion model, and navigation rules in the source or a companion definitions file.
  • Choose a launch file that already exists as a built .html output.
  • Do not leave sequencing, tracking, or completion to the packaging step to invent. Missing decisions block packaging on purpose.

Anatomy of a valid tagged block

<HTML>
Homework 1
<filename>"CP4807-H1.html"</filename>

Design a program that controls
two sets of traffic lights
at a junction.

</HTML>
Opening tag

Sets the output type for this block. Must be one of the recognised tags listed below. The AI uses this to decide what to build.

Display title

Optional. Appears as the heading in the built output. If omitted, the filename stem is used instead.

Filename tag

Required. Must be unique across the entire source document and must include a valid file extension.

Block content

The learner-facing material. Teacher notes and wrapper tags are stripped during the extraction stage.

Closing tag

Must exactly match the opening tag including case. <HTML> must close with </HTML> — not </html>.

Recognised tag types

The opening tag determines what the AI builds. Using an unrecognised tag causes the block to be skipped with a warning.

<HTML>

Learner HTML page

Builds a learner-facing web page. Used for homework, assignments, assessments, and any block that needs a browser-rendered output.

e.g. CP4807-H1.html
Assessment subtype becomes a SCO item in the SCORM manifest.
<worksheet>

Worksheet output

Builds a structured worksheet. Used for in-class activities or any block that needs a printable, downloadable format.

e.g. CP4807-1.docx
Not a SCO — does not become a trackable SCORM item.
<document>

Document output

Builds a reference or supporting document. Used for reading resources, guidance material, and supplementary content.

e.g. CP4807-CPDcert.pdf
Supplementary resource only — not tracked by the LMS.

Recommended authoring pattern for SCORM-ready content

This example shows the kind of source structure that gives the packaging stage the least ambiguity later on.

<HTML>
Assessment 1: Traffic light logic
<filename>"CP4807-A1.html"</filename>

Create a program that controls two sets of traffic lights at a junction.
Your solution must include:
- Red, amber, and green timing
- A safe transition sequence
- A short explanation of your logic

</HTML>

scorm-version: "1.2"
launch: "CP4807-A1.html"
tracking: "completion-and-score"
completion: "quiz-pass"
navigation: "linear"

Best practice: keep the learner page in its own <HTML> block, then define the package-level SCORM settings separately so the launch page and tracking behavior are both explicit.

How to author external resources and teaching links

This tool is designed for teachers who need to combine worksheets with linked resources. External links should be written in a consistent, explicit way so they can be turned into reliable learner-facing launch items or support links.

Videos

YouTube links should be visible, named, and learner-safe

  • Place the link inside the learner block where it is needed, with a clear label such as Video resource: https://youtu.be/....
  • Use a stable watch or share URL, not a temporary browser address.
  • Name the video in the surrounding text so the built output can show a human-readable link label.
Google files

Google Docs and Slides links must be share-ready

  • Use viewable share links, not edit-only links tied to a teacher login.
  • Say what the resource is in plain text, for example Teacher slides: https://docs.google.com/presentation/....
  • If learners need the file, place it in a learner-facing block. If it is teacher-only, keep it in a support resource block instead.
Datasheets

Datasheet and reference links should describe the target clearly

  • Write the resource type and title before the URL, such as Datasheet: PIC16F877A datasheet - https://....
  • Prefer direct PDF or stable vendor links over search-result URLs.
  • If the linked file is essential to the activity, mention that in the learner instructions so the generated page preserves the dependency.
Separation

Keep learner links and teacher links separate

  • Learner-visible links belong inside the learner block they support.
  • Teacher PowerPoints, answer sheets, and delivery notes should go in a separate supporting block, usually <document> or a dedicated teacher resource page.
  • Do not mix teacher-only links into assessment or learner HTML blocks unless learners are meant to see them.
<HTML>
Worksheet 3: Inputs and outputs
<filename>"CP4807-WS3.html"</filename>

Complete the worksheet tasks below.

Video resource: https://youtu.be/h8-7BsXBpLc
Datasheet: PIC16F877A datasheet - https://www.example.com/pic16f877a.pdf
Learner slides: https://docs.google.com/presentation/d/example/view

</HTML>

<document>
Teacher delivery pack
<filename>"CP4807-Teacher-Pack.docx"</filename>

Teacher slides: https://docs.google.com/presentation/d/example/edit
Teacher notes: https://docs.google.com/document/d/example/edit

</document>

Rule of thumb: learner-facing links stay with the learner block; teacher-only links go into a separate support output so the SCORM package does not accidentally expose staff materials.

Filename Rules

Filenames must be unique, correctly typed, and include the right extension.

The filename tag is how the pipeline knows where to write each output. An incorrect or duplicated filename breaks the chain for that block only — the rest of the source continues to process.

Must be unique across the whole source document

No two blocks can share a filename. Duplicates are flagged in the analysis report and the second block is skipped.

Must include a file extension

The extension tells the pipeline which folder to route the output to. Without one the file cannot be placed or built.

Must be wrapped in double quotes inside the tag

The value must be quoted: <filename>"CP4807-H1.html"</filename>. Unquoted filenames may not be parsed correctly.

Extension should match the tag type

An <HTML> block should use .html or .htm. A mismatch creates a routing warning in the analysis report.

SCORM Source Requirements

Five decisions must be defined before SCORM packaging can run.

The pipeline reads these from the source document or a companion definitions file. If any are absent, packaging stops safely and the missing items are listed in the packaging report. For this prototype, SCORM 1.2 is the recommended default unless a target LMS specifically requires SCORM 2004.

1

SCORM version

Use 1.2 by default. Only choose 2004 if the target LMS explicitly requires it. The manifest schema, API calls, and data model differ between versions, so this still needs to be stated clearly.

recommendedscorm-version: "1.2"
2

Launch file

The filename of the first page an LMS should open. Must be one of the built HTML outputs and must already exist before packaging runs.

e.g.launch: "CP4807-H1.html"
3

Tracking model

Whether the LMS tracks completion, score, or both. Determines which SCORM API calls are written into the SCO and how the manifest declares them.

e.g.tracking: "completion-only"
4

Completion model

How the LMS decides a learner has finished. Common options are page-view, quiz-pass, time-based, or manual. Must be explicitly chosen by the author.

e.g.completion: "page-view"
5

Navigation rules

Whether learners can move freely between items or must follow a linear sequence. Affects the manifest organisation and item ordering in the LMS.

e.g.navigation: "free"

All five must be defined. The packaging prompt explicitly checks for each one and stops with a clear error listing what is missing. Partial definitions are not used — the whole packaging stage is deferred until all five are present.

imsmanifest.xml

The manifest is the file that turns built content into a real SCORM package.

imsmanifest.xml is the package map for the LMS. It tells the LMS what the course is called, which file launches first, which items are SCOs, and which resources belong inside the package.

What the manifest must contain

  • A package identifier and basic metadata.
  • An organisation structure showing the launch order or item hierarchy.
  • Resource entries that point to real built files such as HTML pages.
  • SCO or asset declarations that match the chosen tracking approach.

What this prototype already knows

  • The intended SCORM version should default to 1.2.
  • <HTML> blocks are the strongest candidates for launchable SCO content.
  • <filename> gives the exact resource href the manifest would need.
  • Titles and content grouping can support human-readable item labels in the LMS.

Illustrative shape

<manifest identifier="course-package">
  <organizations default="course-org">
    <organization identifier="course-org">
      <item identifier="item-a1" identifierref="res-a1">
        <title>Assessment 1</title>
      </item>
    </organization>
  </organizations>
  <resources>
    <resource identifier="res-a1" href="CP4807-A1.html" />
  </resources>
</manifest>

Why one is not generated yet

  • No real launch file has been designated and built for the package yet.
  • The final SCO structure is still undefined.
  • Tracking, completion, and navigation rules are not fully locked.
  • Not all learner-facing files exist yet, so the resource list would be incomplete.

This project currently describes the manifest requirements, but it does not yet contain a real imsmanifest.xml file. The manifest can only be generated once the package structure and resource list are explicit and complete.

Prompts And Rules

The prompts line up directly with the stage model.

Prompt files

  • `prompt-01-analyse.md` finds blocks, filenames, warnings, and SCORM gaps.
  • `prompt-02-extract.md` creates the staged block files.
  • `prompt-03-build.md` creates learner-facing outputs.
  • `prompt-04-package-scorm.md` stops packaging if the required SCORM decisions are missing.

Rules files

  • `tag-rules.md` defines block recognition and filename binding.
  • `output-rules.md` defines output behavior and naming.
  • `scorm-rules.md` defines minimum requirements and stop conditions.
